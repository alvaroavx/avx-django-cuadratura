# ADR 0005: API HTTP v1 genérica para recibir operaciones

Estado: aceptado (2026-10-12). Decisor: Álvaro.

## Contexto

Plataforma Elemental necesita entregar cada mes sus operaciones y pagos sin que una
persona descargue y cargue un archivo. Otros sistemas podrían conectarse en el
futuro, así que la API la define Cuadratura según sus propias reglas y no se adapta
al formato de un emisor en particular.

## Decisión

- **Una API v1 bajo `/api/v1/`, JSON sobre HTTPS.** La raíz `GET /api/v1/` se
  describe a sí misma: versión, autenticación, contratos con enlace a su esquema y
  endpoints. Con un token válido además informa el cliente y las organizaciones
  habilitadas (id, RUT y razón social), para que el emisor encuentre su destino por RUT.
- **Clientes técnicos (`integrations.ApiClient`).**
  - Cada cliente tiene un `origin_system` único que asigna Cuadratura; `MANUAL` y
    `CASHBOOK_CSV_V1` están reservados.
  - Se autentica con `Authorization: Bearer cdr_<prefijo>_<secreto>`. Solo se guarda
    el SHA-256 del token, y el token se muestra una vez al crearlo o rotarlo.
  - Tiene un usuario técnico inactivo y sin contraseña, que figura como autor en lotes
    y auditoría.
  - Solo opera sobre las organizaciones vinculadas en `ApiClientOrganization`.
  - El alta y la rotación se hacen solo por comando (`create_api_client`,
    `rotate_api_client_token`). El admin permite desactivar clientes y vínculos, no
    crear ni ver tokens.
- **Contrato genérico `cuadratura-operations-v1`.**
  - Esquema en `integrations/contracts/` y servido en
    `/api/v1/contracts/cuadratura-operations-v1.schema.json`.
  - Lleva lote, período, RUT esperado, operaciones con montos CLP enteros
    (`net + vat = total`) y pagos confirmados, más registros excluidos (informativos)
    y un resumen.
  - El origen no viaja en el documento: lo fija el token.
  - Reutiliza la clasificación y la confirmación del receptor Elemental v1, ahora
    parametrizadas por `origin_system`.
- **Los lotes se crean, nunca se confirman por API.**
  - `POST /api/v1/organizations/{id}/periods/{AAAA-MM}/batches/` crea el lote en
    preview (`VALIDATED` o `BLOCKED`) y devuelve el acuse con conteos, totales,
    errores y estado por fila.
  - Una persona con rol de importación confirma en la web, igual que con un archivo.
  - `GET .../batches/{id}/` permite consultar si ya fue confirmado (`COMMITTED`).
- **Idempotencia por `batch_id`.**
  - Reenviar el mismo contenido (se ignora `generated_at`) devuelve el lote existente
    (200).
  - Reutilizar `batch_id` con otro contenido responde 409.
  - Un lote `BLOCKED` no cuenta: se puede reenviar para volver a validarse.
  - Las ventas y pagos siguen siendo únicos por `(organización, origin_system, external_id)`.
- **Errores:** `{"error": {"code", "message", "details"}}` con 401, 403, 404, 400,
  409 (`batch_id_conflict`, `period_closed`), 413 y 415.

## Alternativas descartadas

- **Exponer el contrato `elemental-cuadratura-v1` como API:** ataría la API al
  modelo de Elemental (planes, disciplinas, beneficiarios).
- **Confirmar automáticamente:** saltaría la revisión humana que hoy protege el ledger.
- **Django REST Framework:** cuatro endpoints no justifican una dependencia nueva.
- **`IdempotencyRecord` separado (ADR 0003):** `ImportBatch.source_metadata` ya guarda
  `batch_id` y la huella del contenido.

## Consecuencias

- El archivo `elemental-cuadratura-v1` sigue funcionando. Si un cliente usa
  `origin_system=ELEMENTAL`, comparte identidad con los archivos Elemental, y una
  operación ya importada por archivo aparece como «ya existente».
- Seguridad ampliada en [ADR 0006](0006-seguridad-api.md): firma Ed25519, intentos
  fallidos, límites de frecuencia, vencimiento de tokens, HTTPS obligatorio y un lote
  activo por período.
- No hay endpoints para corregir ni anular operaciones ya confirmadas.

## Verificación contra el código (2026-10-12)

- Implementado en `integrations/` (`models.py`, `services.py`, `api.py`, `urls.py`,
  `contracts/`, `management/commands/`) e `imports/operations_v1.py`.
- `integrations/tests.py` cubre:
  - descubrimiento y esquema;
  - autenticación, rotación y desactivación;
  - lote en revisión y confirmación humana con el origen del cliente;
  - idempotencia, lote bloqueado y reenvío;
  - documentos inválidos;
  - alcance por organización y período cerrado;
  - aislamiento entre clientes;
  - el comando de alta.
- Validado de punta a punta por HTTP contra la base local con la organización ficticia
  «Taller Ficticio SpA». No verificado en producción.
